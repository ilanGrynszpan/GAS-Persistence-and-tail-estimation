# REPORTING.md

# Scientific Reporting Framework

This document defines how reports should be generated by the modelling framework.

Reports are a fundamental part of the scientific workflow.

The objective is not merely to display metrics.

The objective is to communicate scientific conclusions in a clear, reproducible, and logically structured manner.

Reports should always be generated from saved artifacts.

They should never require model re-estimation.

---

# 1. General Philosophy

Reports should tell a coherent scientific story.

Each section should answer one scientific question.

Do not present figures or tables without explaining:

* why they exist;
* what they measure;
* how they should be interpreted;
* what scientific conclusion they support.

The report should guide the reader through the experimental pipeline in the same order that the experiments were performed.

---

# 2. Reports Are Independent From Estimation

Model estimation and report generation are separate tasks.

The report generator should only read previously saved artifacts.

Generating a report should never require:

* optimization;
* likelihood evaluation;
* model fitting;
* score computation.

Users should be able to modify the report manually and regenerate the PDF without repeating expensive computations.

---

# 3. Report Generation Pipeline

The reporting workflow should be

Artifacts

↓

Tables

↓

Figures

↓

LaTeX

↓

PDF

The report should remain fully reproducible from artifacts alone.

---

# 4. Editable Reports

The framework should generate

report.tex

rather than only a PDF.

Users should be able to

* modify the LaTeX manually;
* add discussion;
* adjust formatting;
* regenerate the PDF

without assistance from AI.

The report builder should compile the edited LaTeX directly.

---

# 5. Scientific Storytelling

Reports should follow the scientific workflow.

Each stage answers one question before introducing the next.

Current narrative:

1. Baseline GAS.
2. Dynamic parameter comparison.
3. Score scaling comparison.
4. Weather covariates.
5. Harvey long-short.
6. Climate covariates.
7. Final model comparison.
8. Discussion.

Do not jump between unrelated experiments.

---

# 6. Section Structure

Every major report section should contain

Objective

↓

Mathematical model

↓

Experimental design

↓

Results

↓

Discussion

↓

Conclusion

Readers should never need to infer why an experiment was performed.

---

# 7. Mathematical Presentation

All mathematical notation should be consistent throughout the report.

Explicitly distinguish

* transformed states;
* natural parameters;
* link functions;
* score vectors;
* scaled scores.

Never mix transformed and natural parameter notation.

Whenever a transformed parameter appears, clearly state the transformation.

---

# 8. Figures

Every figure should answer one question.

Avoid figures that simultaneously compare many unrelated metrics.

Each figure should

* use one metric;
* use one scale;
* contain readable labels;
* contain informative captions.

Figure captions should explain

* what is plotted;
* what constitutes good performance;
* how the figure should be interpreted.

---

# 9. Tables

Tables should summarize conclusions rather than duplicate figures.

Avoid excessively large tables.

When many models are evaluated,

report

* top models;
* representative failures;
* summary statistics.

Use landscape pages when necessary.

Avoid overflowing pages.

---

# 10. Evaluation Metrics

Metrics should be grouped logically.

Suggested order:

Calibration

↓

Distributional metrics

↓

Tail metrics

↓

Coverage

↓

Point forecasts

↓

Information criteria

Avoid mixing unrelated metrics within the same table.

---

# 11. In-Sample and Out-of-Sample Results

Clearly separate

In-Sample

and

Out-of-Sample

results.

Do not mix them within the same figure or table.

The report should explicitly state

which diagnostics are

IS only,

OOS only,

or both.

---

# 12. Wet and Dry Days

Whenever meaningful,

report metrics separately for

All observations

↓

Wet days

↓

Dry days

Especially for

* RMSE;
* MAE/MAD;
* CRPS;
* tail scores.

This helps identify whether improvements come from rainfall occurrence or wet-day intensity.

---

# 13. Residual Diagnostics

Residual diagnostics belong in dedicated sections.

Include

* PIT histograms;
* QQ plots;
* quantile residuals;
* residual ACF.

Residual ACF should

* use 400 lags;
* include confidence intervals;
* explicitly state the null hypothesis of zero autocorrelation.

Interpret diagnostics rather than simply displaying them.

---

# 14. Tail Diagnostics

Tail behaviour is central to the project.

The report should emphasize

* high quantile scores;
* threshold-weighted CRPS;
* exceedance Brier scores;
* coverage diagnostics.

Tail diagnostics should receive greater discussion than RMSE.

---

# 15. Model Comparison

Models should be compared according to the scientific question of each stage.

Avoid presenting one enormous ranking table.

Instead,

compare only models relevant to the current stage.

For example,

Weather section

↓

only weather models.

Harvey section

↓

only Harvey models.

Final comparison

↓

stage winners.

---

# 16. Optimization Information

Optimization information should not dominate the report.

Summarize

* optimizer;
* iterations;
* convergence class.

Detailed optimization logs belong in artifacts.

Do not interrupt the scientific narrative with optimizer diagnostics.

---

# 17. Failed Models

Failed models should be documented.

Do not hide failures.

However,

failed models should not dominate the report.

A short summary table is sufficient.

---

# 18. Automatic Figure Generation

Every figure generated for the report should also be saved independently.

Do not embed figures only inside the PDF.

Generated figures should remain reusable.

---

# 19. Automatic Table Generation

Likewise,

every LaTeX table should also exist as

* CSV;
* LaTeX;
* optionally Markdown.

Tables should remain reusable outside the report.

---

# 20. Artifact Reuse

The reporting system should never regenerate statistics already available.

Reuse

* predictions;
* residuals;
* PIT values;
* quantiles;
* metrics;
* diagnostics

from saved artifacts.

---

# 21. Report Metadata

Every report should include

* generation date;
* software version;
* experiment identifier;
* dataset identifier;
* model configuration summary.

This improves reproducibility.

---

# 22. README Integration

When the report is generated,

automatically update a small

Results

section inside the repository README.

The README should contain only a concise summary,

for example

* best model;
* best CRPS;
* best twCRPS;
* best quantile score;
* report location.

Do not place full experimental results inside the README.

---

# 23. Report Templates

The reporting system should support reusable templates.

The same framework should later generate reports for

* precipitation;
* finance;
* volatility;
* insurance;

without changing the reporting engine.

Application-specific sections belong in templates.

---

# 24. Things To Avoid

Avoid

* generating reports directly from optimization;
* inconsistent notation;
* repeated explanations;
* giant tables;
* unreadable figures;
* figures without interpretation;
* metrics without discussion;
* manually copying results into the report;
* hard-coded paths;
* duplicated captions.

---

# 25. Final Principle

A report is the scientific presentation of an experiment.

The report should explain

what was done,

why it was done,

what was observed,

and

what conclusions can reasonably be drawn.

Every figure,

table,

and paragraph

should contribute to answering a scientific question.

Anything that does not support that objective should be omitted.

# 26. Report Validation Checklist

Before a report is considered complete, the reporting framework should automatically validate its consistency.

The objective is to identify common problems before submission or publication.

Validation should be divided into five categories:

* report structure;
* mathematical consistency;
* experimental consistency;
* graphical consistency;
* technical consistency.

A report should not be considered complete until these checks have been performed.

---

# 26.1 Structure Validation

Verify that every major section is present.

Current expected structure:

* Executive Summary
* Introduction
* Experimental Design
* Model Specification
* Results
* Diagnostics
* Discussion
* Conclusion
* References

Every section should contain explanatory text.

Avoid reports consisting primarily of figures and tables.

---

# 26.2 Scientific Narrative Validation

Verify that every experimental stage answers a scientific question.

For every section, confirm that the following progression exists:

Objective

↓

Model

↓

Experiment

↓

Results

↓

Discussion

↓

Conclusion

If any stage is missing, issue a warning.

The report should tell a coherent scientific story rather than presenting disconnected experiments.

---

# 26.3 Mathematical Consistency

Verify that mathematical notation is consistent throughout the report.

Examples include:

* transformed parameters are clearly distinguished from natural parameters;
* link functions are explicitly defined before use;
* score vectors use consistent notation;
* Fisher information notation is consistent;
* parameter names remain unchanged across sections.

Warn if notation changes unexpectedly.

---

# 26.4 Experimental Consistency

Verify that every reported model corresponds to an existing saved artifact.

Confirm that:

* model identifiers exist;
* configuration files exist;
* metrics exist;
* diagnostics exist;
* figures correspond to the reported experiment.

Never allow manually entered numerical results.

All reported values should originate from saved artifacts.

---

# 26.5 Figure Validation

Verify that:

* every figure is referenced in the text;
* every figure has a caption;
* captions explain interpretation;
* axis labels are present;
* units are present where appropriate;
* legends are readable;
* figures have sufficient resolution;
* figure numbering is sequential.

Warn if figures overflow page margins.

---

# 26.6 Table Validation

Verify that:

* every table is referenced in the text;
* every table has a caption;
* table numbering is sequential;
* tables fit within page boundaries;
* landscape pages are used when necessary;
* decimal precision is consistent;
* significant digits are appropriate.

Avoid unnecessary precision.

---

# 26.7 Metric Validation

Verify that every reported metric clearly states:

* whether lower or higher values are better;
* whether the metric is IS or OOS;
* whether the metric is evaluated on

  * all observations;
  * wet days;
  * dry days;

when applicable.

Tail metrics should be clearly identified.

---

# 26.8 Diagnostic Validation

Verify that diagnostic plots are available for selected models.

Examples include:

* PIT histogram;
* QQ plot;
* quantile residuals;
* residual ACF;
* coverage diagnostics.

Residual ACF should:

* use 400 lags;
* display confidence intervals;
* state the null hypothesis of zero autocorrelation.

---

# 26.9 Statistical Consistency

Verify that:

* probability values lie within valid ranges;
* predictive quantiles are ordered;
* coverage values are between 0 and 1;
* RMSE, MAE, CRPS, and twCRPS are finite;
* information criteria are finite.

Warn if numerical inconsistencies are detected.

---

# 26.10 Report Metadata

Verify that the report records:

* report generation date;
* experiment identifier;
* software version;
* dataset identifier;
* configuration summary.

This information should appear automatically in the report.

---

# 26.11 LaTeX Validation

Before PDF generation, verify that:

* all references resolve;
* all citations resolve;
* all equations compile;
* no missing figures exist;
* no missing tables exist;
* bibliography compiles successfully;
* page references are valid.

Compilation warnings should be recorded.

---

# 26.12 Artifact Validation

Confirm that every figure and table included in the report also exists as an independent artifact.

Examples:

* figures as PDF and PNG;
* tables as LaTeX and CSV.

The report should never become the only source of a result.

---

# 26.13 README Validation

Before updating the repository README,

verify that:

* reported best model exists;
* reported metrics correspond to saved artifacts;
* links remain valid.

The README should summarize the current best results only.

---

# 26.14 Final Validation Summary

After all checks, generate a concise validation report.

Example:

PASS

✓ Report structure

✓ Mathematical notation

✓ Figures

✓ Tables

✓ Diagnostics

✓ Metrics

✓ References

✓ Artifact consistency

Warnings

• Two figures use different decimal precision.

• One table exceeds recommended page width.

Errors

None

If warnings or errors exist, they should be reported before final PDF generation.

---

# 26.15 Final Principle

The reporting framework should verify not only that the report compiles, but also that it is scientifically consistent.

Automatic validation cannot replace scientific judgement.

Its purpose is to detect technical inconsistencies, improve reproducibility, and reduce avoidable mistakes before publication or thesis submission.
